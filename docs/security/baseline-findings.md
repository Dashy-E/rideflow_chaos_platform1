# Security baseline — first full run against the reference implementation

Generated by running all 6 attacks in `security-injector/` against the local
docker-compose stack. This is exactly the kind of evidence doc §3.2's note
("cite evidence, not just description") asks for — keep this file updated
as you fix things, and it becomes a real before/after story for the report.

| Attack | Verdict | Summary |
|---|---|---|
| `rate-limit-pressure-gateway` | ✅ defended (after fix) | Gateway's per-IP token bucket throttled 89/240 requests in a burst. **Originally failed**: the rate limiter keyed on `r.RemoteAddr`, which includes the ephemeral source port and is different on every connection — every request got a fresh, full bucket. Fixed in `services/api-gateway/main.go` (`clientIP()` now strips the port via `net.SplitHostPort`). |
| `injection-fuzz-ride-service` | ✅ defended | 8/8 SQLi/XSS/command-injection-style and oversized payloads handled without a 5xx or stack-trace disclosure. |
| `jwt-tampering-user-service` | ⚠️ partial | `alg:none`, garbage signatures, and stale-signature payload tampering are all correctly rejected. **One real finding**: a token forged with the *hardcoded default* `JWT_SECRET` fallback in `services/user-service/src/index.js` is accepted. This is fine for local dev but is a **critical** finding if that default ever ships to a real deployment — `JWT_SECRET` must be overridden via a real secret (AWS Secrets Manager / K8s Secret + IRSA), never left at its source default. |
| `auth-bruteforce-user-service` | ⚠️ partial | 25 wrong-password attempts against one account, all handled normally with no lockout or auth-specific rate limiting. The generic gateway rate limiter is IP-based and would not stop a slow or distributed brute-force. **Recommended fix** (not yet implemented): per-account exponential backoff or lockout after N failed attempts in `user-service`. |
| `idor-probe-ride-service` | ❌ vulnerable | Two real findings: (1) `GET /v1/rides/{id}` has no per-user ownership check — any caller can read any ride by ID. (2) `ride-service`'s `/internal/*` API has zero auth of its own and is fully reachable directly, bypassing `api-gateway`'s JWT check entirely. Documented as a known architectural gap (doc §15.1 explicitly scopes out a service mesh), not silently relied on — closing this needs either per-ride ownership checks in `ride-service`, or a NetworkPolicy/mTLS layer between services. |
| `internal-endpoint-recon` | ❌ vulnerable (expected locally) | All `/internal/*` and `/admin/*` endpoints are directly reachable on their own container ports. **Expected** in this docker-compose topology (every port is published to the host for demoability). In the real EKS deployment, verify this does NOT hold: only `api-gateway` should have an ALB target group; everything else should only be reachable from inside the cluster network — check with a NetworkPolicy or by inspecting Service types. |

## Score at last run

**Overall: 33% → recommend re-running after applying the two "recommended fix" items above** (account lockout, per-ride ownership check) to see the number move — that delta is a strong report artifact on its own.

## Honest scope note

This is a lightweight, purpose-built scanner covering six categories relevant
to *this* app's actual attack surface — it is not a substitute for a real
DAST/SAST tool or a professional pentest, and it doesn't cover things like
TLS configuration, dependency CVEs (already covered separately by Trivy in
CI), or infrastructure-level misconfiguration. Framed honestly in the report
as "we built a targeted tool for the vulnerability classes most relevant to
a microservices ride-hailing backend," not as a general security audit.
